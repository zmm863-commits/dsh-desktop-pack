## 二、Windows 构建

一键重建：`/root/dshpack-017/win/rebuild.sh`

### 本机 NSIS 3.08 的三个坑（都实测过）

**坑 1 · locale（最隐蔽）**
默认 `POSIX`/`C` 环境下，`makensis` 遇到**任何非 ASCII 字符**（中文文件名、
中文 UI 串）都会**段错误**（exit 139，日志只打印到 “Processing script file”）。
必须 `LC_ALL=C.UTF-8 makensis installer.nsi`。

> 这一条同时解释了旧会话的两个误判：
> 「Linux 上 `File /r` 会段错误」——其实是 locale；
> 「中文文件名已转为英文」——也不必转，加 locale 即可。
> 用 `LC_ALL=C.UTF-8` 后 `File /r`、中文路径、中文 UI 串全部正常。

**坑 2 · 构建目录必须干净**
`makensis` 处理 `File /r "<目录>"` 时会连带遍历该目录**父目录里的兄弟目录**。
在 `/root/dshpack-017/win` 直接编译，会把构建暂存目录 `tpl/`、`tpl2/`
一起打进安装包（实测多出 806 个条目、未压缩体积多 **87MB**）。
解决：先把 payload 单独复制到 `/root/dshpack-017/win-build/` 再编译，
这样即便发生兄弟目录遍历，被遍历到的也只有 payload。

**坑 3 · payload 内不能有指向外部的绝对符号链接**
`dsh-agnes-studio/node_modules/@deepseek-ai/` 下有 6 个指向 `/dsh/...` 的
npm 链接（本机开发环境产物）。NSIS 会跟随链接把外部内容打包；而在用户机器上
这些链接本身就是**死链**。必须先实体化成真实目录（`rebuild.sh` 第 1 步自动处理）。

**另注**：`SetCompressor /solid lzma` 与 `bzip2` 在本机 NSIS 3.08 上同样段错误，
安装脚本使用默认 `zlib`。

### 逐文件清单 vs File /r

旧会话用的是构建期生成的逐文件清单（40831 行）。现在确认那是 locale 问题导致的
误判——用 `LC_ALL=C.UTF-8` 后 `File /r` 即可，脚本从 46000+ 行回到 174 行，
这也是 2.3.2 验证过的写法。同时恢复了被误删的 `launcher/version.txt` 写入块
（`launcher/start.ps1` 依赖它判断是否要把新版程序同步进 `%APPDATA%`）。

## 三、macOS 构建

打包脚本：`/root/dshpack-017/mac/mkzip.py`（沿用 2.3.2 技术文档 7.3 的写法）

```bash
cd /root/dshpack-017/mac
python3 mkzip.py dist/PaopaocatDSH.app dist/PaopaocatDSH-macOS-v3.1.15-universal.zip
```

要点：

1. **符号链接必须单独成条目**：`ZipFile.write()` 会把链接存成实体副本
   （`python3` 从 10 字节变 17MB）。必须手工构造 `ZipInfo`：
   `external_attr = S_IFLNK|0o777`、`compress_type = ZIP_STORED`、内容 = 链接目标。
   脚本同时会体检「指向绝对路径的符号链接」，有死链直接报错退出。
2. **`--expose-internals` 必须保留**（命令行参数形式，`NODE_OPTIONS` 无效）——
   这是绕开 `node-addon-require-builtin` 要求 macOS 15 的关键，最低系统才能到 11.0。
3. 版本号有 **3 处**要同步：`launcher/start.command` 的 `VERSION=`、
   `launcher/version.txt`、`Contents/Info.plist` 的 `CFBundleShortVersionString`/`CFBundleVersion`。
4. 需先实体化 `.app` 与模板目录里指向 `/dsh/...` 的 6 个绝对链接。

产物：

| 文件 | 说明 |
|---|---|
| `PaopaocatDSH-macOS-v3.1.15-universal.zip` | 主安装包（573.5MB） |
| `PaopaocatDSH-macOS-v3.1.15-脚本安装.zip` | 脚本安装形态 = 安装脚本 + 使用说明 + 上面的 zip |

**按用户要求，macOS 不再提供 tar.gz。**

## 六、真机反馈修复：三个插件 failed to import

**真机现象**（Windows 覆盖安装后启动）：
`dsh: warning: 1 entry did not activate` / `agnes-studio (dsh-agnes-studio): failed to import`

**本机复现**（在打包后的 profile 目录里直接 import）：

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@deepseek-ai/dsh-scope'
  imported from .../dsh-agnes-studio/node_modules/@deepseek-ai/dsh-skill/lib/index.js
```

并顺带查出另外两个插件同样坏掉：`dsh-vision-router`（缺
`@deepseek-ai/dsh-llm-deepseek`）、`@michengai/dsh-automation`（缺
`@deepseek-ai/dsh-workspace`）。

**根因**：开发环境的依赖解析靠 `/dsh/profiles/node_modules` —— 这是一层
**提升（hoist）目录**，187 个条目里有 164 个是指向全局 DSH 依赖的符号链接
（240 个 `@deepseek-ai/*`）。打包时只带了 `profiles/web/`，**整层缺失**，
于是插件嵌套包的 peer / 传递依赖无处解析。

另外 `dsh-agnes-studio/node_modules/@deepseek-ai/` 下还残留着 10 个**来自旧版全局
安装**的嵌套副本（`cosmokit@1.8.3`、`cordis@4.0.2`，而随包 app 是 `1.8.5`/
`4.0.4`），既会引发版本冲突（`schemastery` 要 `cosmokit` 导出 `createVolatile`），
又掩盖了提升层缺失的问题。

> 这**不是 3.1.6 引入的回归**：2.3.3、3.1.2 的包同样只有 `profiles/web`。
> （3.1.6 是首次交付版；因为它先被装过一次，修复改为 **3.1.7** 重新发布，
> 以「版本变化」触发启动器同步——见下方守卫说明。）
> 之前没暴露，是因为旧版 `dsh-agnes-studio` 的嵌套依赖更少；本次 agnes-studio
> 引入了 `@deepseek-ai/dsh-skill`（peer 依赖 `dsh-scope`）才把它顶出来。

**修复**（脚本 `fix-profile-deps.py`，已接入 `win/rebuild.sh` 第 0 步）：

1. 移除并备份 `dsh-agnes-studio/node_modules/@deepseek-ai/` 下的嵌套旧副本
   （备份在 `backups/nested-at-deepseek-ai-*`，可回滚）。
2. 逐个 `import` profile 里声明的每个插件，缺什么就从**随包 `app/node_modules`**
   复制什么到 `data-template/profiles/node_modules/`（= 与 dev 对应的提升层），
   迭代到全部通过。全部取自随包 app，保证版本自洽。

结果：提升层 12MB（`@deepseek-ai` 26 个包 + `zod` + `eventsource-parser`），
**16 个非基础插件全部 import 通过**。

**验证升级**（针对最终交付物本体，而非构建中间态）：

- [x] 新增「逐个插件 import 检查」，并改为对 **7z 抽出的最终包**执行 →
      Windows 与 macOS 均为 **0/16 失败**
- [x] Windows 包再次完整抽取做 md5 比对：**61,056 个文件全部一致**，无多无少
- [x] macOS 包解出后同样跑插件检查 → **0/16 失败**
- [x] 顺带修掉启动器横幅硬编码的旧版本串（Windows `start.ps1` 与
      mac `start.command` 注释仍写 v3.1.2）

**升级安装也会生效**：`win/launcher/start.ps1` 的覆盖安装分支用
`robocopy $tpl $data /E`，新增的 `profiles/node_modules` 会一并同步进

**版本号最终定为 3.1.7**：真机上 3.1.6 已装过一次，同名版本会被判定

升到 3.1.7 后按「版本变化」必然触发同步。

**⚠️ 额外加的守卫**：启动器原先只在「版本号变化」时同步程序文件。因为本次修复
3.1.6 已在那台机器上装过一次，同名版本会判定「已是最新」而不去补这个层

- 层里放一个标记文件 `profiles/node_modules/.paopaocat-deps-layer`（内容

验证：从两个最终包里分别取出启动器，确认守卫代码在包内；再对**解包后的最终
交付物**逐个 import 插件，Windows 与 macOS 均 **16/16 通过**。

## 七、真正的根因：旧版残留污染（3.1.8 修复）

3.1.6 / 3.1.7 都没修好真机上的 `agnes-studio: failed to import`，因为**前面几次都改错了地方**。
真正的原因是**旧文件残留**：

### 现象与证明

在干净 payload 上做注入实验（可复现）：

| 场景 | `import('dsh-agnes-studio')` |
|---|---|
| 干净 profile | ✅ OK |
| 注入旧版嵌套 `@deepseek-ai`（cosmokit **1.8.3**，层里是 1.8.5） | ❌ `The requested module '@deepseek-ai/cosmokit' does not provide an export named 'createVolatile'` |
| 清掉残留 | ✅ OK |

### 为什么残留清不掉

用户第一次装的 3.1.6 包里，插件目录下带着**旧的嵌套 `@deepseek-ai` 副本**
（`cosmokit 1.8.3` / `cordis 4.0.2`，比随包 app 的 1.8.5 / 4.0.4 旧）。它们被写进了

1. **安装目录** `D:\Programs\PaopaocatDSH\data-template\...`，以及
2. **数据目录** `%APPDATA%\PaopaocatDSH\profiles\web\node_modules\...`

而 **NSIS 安装器、robocopy、rsync 全都是「只覆盖、不删除」**：

- 后续版本把包里的嵌套副本删掉了（这没错），但安装目录/数据目录里的旧文件一直留着；
- 同步时 `robocopy /E` 又把「安装目录里的旧文件」原样带进数据目录。

于是每次启动，`dsh-agnes-studio/node_modules/@deepseek-ai/dsh-skill` 仍会解析到那个
**旧 cosmokit**，加载即失败。这也解释了为什么本机（干净 payload）每次验证都通过。

### 修复

1. **安装器**（`installer.nsi`）：覆盖安装前 `RMDir /r` 清空
   `app` / `node` / `git` / `launcher` / `data-template`，杜绝旧文件混入。
2. **Windows 启动器**（`start.ps1`）：同步前整层删除
   `profiles\web\node_modules` 与 `profiles\node_modules`，再整层拷入。
3. **macOS 启动器**（`start.command`）：同步前 `rm -rf` 同样两处目录。
4. **构建不变量**（`win/rebuild.sh`）：若包内出现任何**嵌套** `@deepseek-ai`
   （即会遮蔽提升层的那种），直接构建失败。此检查当场还揪出了
   `dsh-client-ui-paopaocat` 下同样残留的 `cosmokit 1.8.3` / `cordis 4.0.2`，已一并清除。
5. **版本号 3.1.7 → 3.1.8**，层标记 `3.1.7-layer1` → `3.1.8-layer2`，
   保证真机上按「版本变化」或「标记不符」都能触发同步。

### 端到端模拟验证（本机）

1. 造一个与真机等价的「脏」数据目录：无提升层 + 两处旧嵌套副本；
2. 复现失败：`Cannot find package '@deepseek-ai/dsh-scope'`（与真机症状同源）；
3. 执行新版启动器的同步动作（清空两个 `node_modules` + 按模板覆盖拷入）；
4. 结果：**16 个非基础插件全部 import 通过**，残留归零，提升层与标记就位。

## 八、界面打不开（HTTP 400）的根因与修复（3.1.9）

真机反馈：启动日志完全正常、插件不再报 `failed to import`，但**浏览器显示
`HTTP ERROR 400`，界面打不开**。

### 定位过程（本机完整复现）

1. 启动 payload，用 curl 走完整认证链：
   `GET /?token=<正确>` → **303 + Set-Cookie**；随后带 cookie `GET /` →
   **400 Bad Request，空 body** —— 与真机现象一致（Chrome 对空 body 的 400 就显示
   `HTTP ERROR 400`）。
2. 该 400 来自 `dsh-host-webserver` 的兜底错误处理器：请求处理**抛异常**时
   `res.writeHead(400); res.end()`，并把异常交给 `logger.warn`（默认不打印到控制台，
   所以日志里看不到原因）。
3. 代码审读发现 `profiles/web/node_modules` 里存在 **旧版核心包**：
   `@deepseek-ai/dsh-host-webserver` = **0.1.0-rc.8**（7429 字节），
   而随包 app 是 **0.1.7-rc.2**（13335 字节）。插件解析优先用 profile 内那份 →
   **旧 webserver 配 0.1.7 的认证/连接层** → 每个页面请求都崩溃 → 空 body 400。
4. 审计全部 43 个 `@deepseek-ai/*`：**只有这一个版本错配**。
5. 删掉该旧副本（改由提升层提供 0.1.7-rc.2，与 dev 环境一致）后，
   同一套 curl 链：`GET /` → **200 + 392,957 字节真实 HTML**，静态资源 200 ✅。

> 这与 3.1.8 修的「旧版残留」是**同一类病**（旧文件遮蔽新版），但位置不同：
> 这次藏在 payload 自带的 `profiles/web/node_modules` 里，随包发布，与用户机器无关。

### 修复

- 删除 win / mac payload 中 `profiles/web/node_modules/@deepseek-ai/dsh-host-webserver`
  （0.1.0-rc.8），备份在 `backups/stale-*-dsh-host-webserver-0.1.0-rc.8/`。
- **新增 payload 三重校验**（`verify-payload.py`，已接入 `win/rebuild.sh` 第 5 步）：
  1. **版本一致性审计**：`profiles/web/node_modules` 里每个 `@deepseek-ai/*`
     必须与随包 app 版本一致；
  2. 逐个插件 import；
  3. **HTTP 冒烟**：真启动一次，走 token → cookie → 首页，断言拿到 200 的真实 HTML。

> ⚠️ 关键教训：**只查 import 抓不到这个 bug**。实测在带旧 webserver 的包上，
> 插件 import 依然 **16/16 通过**，但首页 400。必须加上版本审计与 HTTP 冒烟。

### 我自己工具的两个缺陷（已修，并记录以免重犯）

写 `verify-payload.py` 时踩了两个坑，其中一个**污染了 payload**：

1. 临时 DSH_HOME 用 `cp -al` 建在 `/root`，而校验对象在 `/tmp`（跨文件系统）→
   硬链接失败但被忽略 → home 残缺 → 误报插件 `failed to import`。
   已改为：临时目录放在 payload **同级**（保证同文件系统），失败时回退真实拷贝。
2. 为让冒烟测试不与真机 3080 冲突，需要改测试 home 的端口；但 home 与 payload
   共享 inode（硬链接），**就地改写把源 payload 的 `cordis.patch.yml` 端口也改成了
   随机值**（应从 3080 变成 36311）。已改为「先删再写」断开硬链接，
   并在校验结束时**断言 payload 未被改动**。修复后已把两端端口改回 3080。

## 九、内置 Mnemon CLI（3.1.10）

真机反馈：界面能打开了，但记忆插件里显示 **「未找到 Mnemon CLI」**。

### 这是什么

`mnemon` 是长期记忆库的**独立命令行工具**（npm 包 `@mnemon-dev/mnemon`：44KB 的 JS 启动器
+ 各平台原生包 `mnemon-<platform>-<arch>`，约 16MB）。插件用它做**记忆空间的存储操作**
（`execute()` 包在 `withMemoryStorageLock` 里，通过 `spawn` 调用），
以及组件/版本检查。插件查找顺序是：

`mnemon.cliPath` 配置 → 环境变量 `MNEMON_CLI_PATH` → `PATH` 里的 `mnemon`
→ 各平台常见安装路径（Windows 查 `%LOCALAPPDATA%\Programs\mnemon`、`%ProgramFiles%\mnemon`、Go bin 等）。

### 根因：不是用户没装，是包漏带了

开发环境的 `profiles/web/cordis.patch.yml` 里**显式配置**了：

```yaml
cliPath: /dsh/mnemon-cli/node_modules/@mnemon-dev/mnemon/bin/mnemon.js
```

而我们的 payload **既没有这段配置、也没有 CLI 本体** → 插件判定 missing。
按「版本口径 = 本机正在运行的状态」，这属于打包漏项。

### 修复

1. 随包内置 CLI：`data-template/mnemon-cli/node_modules/@mnemon-dev/`
   - Windows：`mnemon` + `mnemon-win32-x64`（约 14MB）
   - macOS：`mnemon` + `mnemon-darwin-arm64` + `mnemon-darwin-x64`（约 31MB，通用包）
2. 启动器注入环境变量（不写死绝对路径，缺失时不设置、可回退到用户自装的 mnemon）：
   - `start.ps1`：`$env:MNEMON_CLI_PATH = "$data\mnemon-cli\node_modules\@mnemon-dev\mnemon\bin\mnemon.js"`
   - `start.command`：`export MNEMON_CLI_PATH="$DATA/mnemon-cli/.../bin/mnemon.js"`
3. 校验脚本新增两项检查：内置 CLI 完整（启动器 + **目标平台**二进制包）、
   **用插件自己的 `findMnemonCommand`/`mnemonNpmLauncher` 按 win32/darwin 平台确认可识别**
   （因此不必真机即可验证；本机另用 linux 版实测 `node <launcher> --version` → `mnemon version 0.2.8`）。

> 影响面：CLI 只服务**记忆空间的存储操作**与组件检查。运行时记忆（MEMORY/USER）、
> 文档（documents）、非原生 provider 都是进程内 JS，不受影响。

## 十一、启动阶段的设置导入锁竞争（3.1.11 修复）

真机日志：

```
[dsh-agnes-studio] Oh Story host half lost the duplicate-registration race ...
dsh-mnemon: DSH is importing settings.yaml; restart once to recover ...
[agency-agents] 旧设置导入失败，数据仍保留在 settings.yaml.imported：
  Error: atomic-write: timed out waiting for the writer lock at
  C:\Users\25894\AppData\Roaming\PaopaocatDSH\profiles\web\package.json.lock
    at withFileLock (.../dsh-atomic-write/lib/index.js:206:37)
    at async run (.../dsh-config-editor/lib/index.js:66:4)
```

### 机制

- Mnemon 首次接管 `settings.yaml` 时会**导入并改名**为 `settings.yaml.imported`；
- `@michengai/dsh-agency-agents` 也在启动时通过 `recoverImportedAgencySettings`
  从旧设置恢复自己的配置（`lib/src-*.js` 的 effect），走 settings API →
  `dsh-config-editor` → 抢 **`profiles/web/package.json.lock`**；
- `dsh-atomic-write` 的写锁**默认只等 200ms**（`LOCK_RETRY_INITIAL_MS=20`、
  `LOCK_RETRY_MAX_MS=200`，默认等待取常量），Windows 上很容易超时 →
  输的那方打印该告警。

### 真正的触发源：启动器每次重建 settings.yaml

实测（连续三次启动，同一台机器）：

| 启动 | 是否先重建 settings.yaml | mnemon 重复导入 | agency-agents 报错 |
|---|---|---|---|
| 第 1 次 | 否（首次） | 1 次 | 0（竞争是时序性的） |
| 第 2 次 | **是** | **又 1 次** | 0 |
| 第 3 次 | 否 | **0 次** | 0，启动正常 |

也就是说：**启动器每次发现 `settings.yaml` 缺失就从模板重建**，于是每启动一次就
重演一次「旧设置导入」；两个插件同时抢锁，必然偶发超时。这属于启动器行为，不是插件缺陷。

### 修复

启动器改为：**存在 `settings.yaml.imported` 时不再重建 `settings.yaml`**
（即 Mnemon 已接管后就不再插回模板）：

- Windows `start.ps1`：`if (Test-Path $settingsImported) { 跳过重建 }`
- macOS `start.command`：`if [ -f "$SETTINGS_IMPORTED" ]; then 跳过重建`

用**真实脚本片段**做两种情形验证（从 start.command 抽出 step3 段落直接 eval）：

| 情形 | 结果 |
|---|---|
| 无 settings.yaml、无 .imported（首次安装） | 从模板创建 ✅ |
| 无 settings.yaml、有 .imported（已接管） | 跳过重建 ✅（不再触发导入竞争） |

### 影响说明（给用户的答复）

该告警**不丢数据**：配置仍保留在 `settings.yaml.imported`，agency-agents 每次启动都会
重试恢复；修复后不再反复触发，下一次启动即静默成功。属于提示性告警，不影响已装载插件
的功能。

### 顺带加固了校验脚本

`verify-payload.py` 之前在某项检查被**跳过**时仍按「通过」计数（本次就出现过：
linux 原生绑定缓存被清理后 HTTP 冒烟被静默跳过）。现已改为：跳过的检查单独记为
`未执行`，结论会明确写出「已完成检查全部通过，但有 N 项未执行」，
不再把跳过当通过。同时新增**启动器守卫检查**（`settings.yaml.imported` 守卫、
`MNEMON_CLI_PATH` 注入、依赖提升层守卫），三项齐全才算通过。

## 十二、macOS 11~14 启动失败：原生绑定不可用（3.1.12 修复）

真机日志（Intel iMac，`arch = x64`）：

```
dsh: fatal uncaught exception: Error: dsh: host preparation failed:
  No usable native binding found for node-addon-require-builtin-darwin-x64 (auto)
  ... attempts: optional-package … No usable prebuilt binary found in darwin-x64
```

### 根因：交接文档里的绕行结论不完整

`node-modules/@deepseek-ai` 侧一直依赖「给 node 加 `--expose-internals`」来绕开这个原生库。
实测该绕行**只覆盖 `cordis-plugin-loader`**：

```js
// cordis-plugin-loader/lib/index.js
function requireInternal(id) {
  if (process.execArgv.includes("--expose-internals")) try { return require(id) } catch {}
  try { return require("node-addon-require-builtin").requireBuiltin(id) } catch {}
}
```

而 **DSH 0.1.7 的 `dsh-app-boot` 是无条件 require 它**（`lib/index.js:1574`）：

```js
const addon = createRequire(import.meta.url)("node-addon-require-builtin");
const esmModule = addon.requireBuiltin("internal/modules/esm/loader");
```

0.1.5 时代没有这一步，所以 2.3.2 的 `--expose-internals` 方案当时成立；升级到 0.1.7 后失效。

而官方 darwin 预编译二进制**本身要求 macOS 15**（本机用 Mach-O 解析确认）：

| 包 | LC_BUILD_VERSION minos | 代码签名 |
|---|---|---|
| `node-addon-require-builtin-darwin-x64` | **15.0.0**（sdk 15.5） | 无 |
| `node-addon-require-builtin-darwin-arm64` | **15.0.0**（sdk 15.5） | **有** LC_CODE_SIGNATURE |

所以在 macOS 11~14 上：dlopen 被拒 → 兜底本地构建也不存在 → host preparation failed。
（arm64 版改字节会破坏签名，因此「打补丁降 minos」对 Apple Silicon 也不通用。）

### 修复：给该模块加 JS 回退实现

替换 `app/node_modules/node-addon-require-builtin/lib/index.js`（原文件备份到
`backups/orig-node-addon-require-builtin-index.js`）：

1. **优先**调用官方 `createEntryApi`（原生可用时行为完全不变）；
2. 原生不可用、且 `process.execArgv` 含 `--expose-internals` 时，
   退回到 `createRequire(__filename)` + `require('internal/…')`
   —— **与 `cordis-plugin-loader` 用的是同一机制**；
3. 两个接口 `isAllowedInternalId` / `getBindingInfo` 全 app 无人调用，
   仅做同形实现，避免契约漂移。

macOS 启动器本来就带 `--expose-internals`，因此无需改动启动器；Windows 侧原生可用，
**未做改动**（不碰正在工作的路径）。

### 验证（本机等价复现）

本机（Linux）同样加载不了 darwin 预编译，与旧版 macOS 走同一条失败路径，因此可直接验证：

- 把垫片放进 mac payload，用 `node --expose-internals app/lib/bin.js web` 启动 →
  **DSH 正常启动**，`GET /` → **200 · 396,373 字节 HTML**；
- 校验脚本的 HTTP 冒烟改为：**darwin payload 故意不安装 linux 预编译**，
  强制走垫片路径（输出会明确打印 `darwin payload：不安装 linux 预编译，验证 JS 回退垫片路径`），
  仍然 200 通过；
- 两端最终交付物全项通过（版本一致性 / 16 个插件 import / 内置 Mnemon CLI 可识别 / 启动器守卫 / HTTP 冒烟）。

## 十四、macOS 弹「下载 git 工具」框（3.1.14 修复）

真机现象（macOS 11.7.11，未安装命令行开发者工具）：DSH 起来后，一打开界面就弹出
「需要安装命令行开发者工具」的系统下载框。

### 机制

- macOS 自带的 `/usr/bin/git` 只是**占位桩**，在未装 CLT 的机器上一执行就等于请求安装 → 弹框；
- DSH 的 `dsh-workspace-changes` 插件在**会话事件**（`session/event`、`tools/pre-execute` 等）
  里运行 `git rev-parse --show-toplevel --absolute-git-dir --git-path objects` 以定位仓库；
- DSH 其实**已经想避开这个坑**（`resolveGit` 在 darwin 上若解析到 `/usr/bin/git`
  会先跑 `/usr/bin/xcode-select -p`，退出码非 0 就不用它），但在本机该探测**返回 0**，
  于是它采信了占位桩 → 调用 → 弹框。属启发式判断在「未装 CLT」机器上失效。

### 修复：内置 git 包装器（PATH 前置）

新增 `Contents/Resources/launcher/bin/git`，启动器把它放在 PATH 最前面：

1. **有真 git**（CLT / Xcode 的 `$(xcode-select -p)/usr/bin/git`，或 Homebrew 的
   `/opt/homebrew/bin/git`、`/usr/local/bin/git`）→ 直接 `exec` 转发，**功能完全不变**；
2. **没有** → 打印可执行的解决办法（`xcode-select --install`）并以 **127** 退出，
   **绝不触碰 `/usr/bin/git` 占位桩** → 不再弹框。

副作用：`dsh-workspace-changes` 会得到一次失败并记一条 `workspace-changes:` 警告，
工作区变更视图为空；其余功能不受影响。

### 验证（本机三分支可控测试）

| 分支 | 构造 | 结果 |
|---|---|---|
| 无 CLT、无 Homebrew git | PATH 只留系统基础目录 | 退出 127 + 打印 `xcode-select --install` 提示，**未调用其它 git** |
| 已装 CLT | 假 `xcode-select` 指向含 git 的 devdir | 退出 0，版本输出来自 devdir 的真 git |
| 参数透传 | `git rev-parse --show-toplevel --absolute-git-dir` | 三个参数原样转发给真 git |
